The lessons

One failure, many disguises

Most of what went wrong on this engagement was the same thing going wrong repeatedly: a check that passes without ever exercising the thing it names. It is worse than having no check, because it converts “we don't know” into “we verified it” — and nobody looks again.

01The catalogue

Real instances from one engagement, in the order we met them. In every case the check was green.

What the green claimedWhat the check could actually detect
Rows come back correctly sorted Nothing — the table was empty, and an empty list equals a sorted empty list whether or not the code sorts
These pieces were never checked They had been — the report rebuilt its index from scratch each run and erased the other results
This screen reads the right table Its twin table held identical rows, so reading the wrong one produced identical output for days
The import permission is correctly enforced No import route existed at all — a permission verified over a mechanism never built
The document matches reality It matched a value measured moments earlier — the check compared reality against itself
“Build succeeded” Half the projects — the solution file had never included the API, so the build check never compiled it
Every check passes on this screen None of them looked at the second table the edit was supposed to cascade into — the one every report reads
Screen labels match the legacy The expected labels had been copied from the rebuild's own menu — the check compared the application against a copy of itself, through run after green run

The last one deserves its own name: the circular oracle. The check was not empty — it asserted real strings against a real page. It was circular: expected values sourced from the thing under test. Nothing short of going back to the original system could catch it.

02The rule: make the judge fail first

The discipline

Before trusting any check, break the code on purpose and watch the check go red. Late in our engagement this became routine, and the reports read differently: “removing one authorization gate tripped a precise, repeatable set of checks; removing a second tripped a different set that barely overlapped; swapping a hand-written scoping rule for the generic one tripped exactly the checks that guard it.” That behaviour is what a trustworthy green looks like — a green that has been red for the right reasons.

We later found the same rule stated independently in Anthropic's write-up of their own large-scale migrations — “validate the judge first: prove the harness passes the original code and fails deliberately broken code” — and, in older words, in Michael Feathers' twenty-year-old advice to write a characterization test you know is wrong and watch it fail before you trust it. Independent convergence from a 2004 book and a 2026 automated migration is about as strong as evidence gets in this field.

03The oracle hierarchy

A check is worth exactly what its oracle is worth. Ours climbed this ladder the hard way.

OracleProvesSilent about
The new system's own output, re-asserted Nothing — circularEverything
The database, queried directly The rebuild reads storage correctly Whether it shows what the old system showed; all computation
The legacy application, running side by side Behavioural equivalence on everything you exercise Only what your inputs never reach
The legacy application plus a second copy of itself Equivalence, with the system's natural noise measured and subtracted — the trick Twitter's Diffy proxy introduced The least of any option

And the fixture matters as much as the oracle. Our worst fixture was two records that were byte-for-byte the same case — it could falsify almost nothing. A fixture earns its keep by being adversarial: rows in reverse display order so a missing sort fails, more rows than the page size so paging is exercised, both populations, both workflow routes, the deleted and the voided and the edge cases — seeded on purpose, checked before being believed.

04Numbers nobody derived

The second recurring failure: a figure written down once and quoted for months.

The numberWhat it was taken to meanWhat it actually was
“8 batch jobs”The programs to rebuild Four true counts in one costume — repositories, executables, scheduled registrations, and jobs that actually recur, no two equal. One nightly job appeared in no list anywhere.
“The screen list”The work remaining What a crawler photographed. Half the features had no screen to photograph.
“The feature count”What the system does The chapter headings of one specification. Everything inside a chapter, or built after it, had no row.
“A healthy percentage done”Real progress One feature started. Same work, honest denominator.
The rule

Anything a plan depends on must be derived from an artifact that changes when reality changes — a routing table, a scheduler export, a database catalogue — by a script that fails loudly when they disagree. And give every such script counterexamples of deliberately different shapes that it must find before it prints anything: every confident wrong answer our scanners ever produced was an under-count, silent by construction.

05Five smaller lessons that paid rent

Open the running system before believing any reading of it

We read one screen's source twice and concluded a feature was missing. Twenty minutes logged into the running application settled it: the feature had been on screen the whole time, on a page our plan had indexed under the wrong name — and the “missing” screen was a mock of something else entirely. Static analysis can tell you a screen is fake; only the running system can tell you which feature it is faking. Both screens existed. Both compiled. The error lived in the index, where no amount of code-reading could find it.

Investigate, never invent

A handful of features had no trace on any source. The instruction that saved us: find out why — write no production code. All five existed. One was fully configured in production. Two “catastrophic” documented risks were simply false. An agent — human or otherwise — sent to build the missing thing would have invented every one of them — features that already existed — differently.

Honest failure beats faked success — and must be said out loud

The single best behaviour we institutionalised: workers report built / partial / blocked / plan-wrong with evidence, and an integration step that finds nothing to integrate says so as its headline rather than manufacturing an empty commit. You get the truth you reward. Tell workers a precise failure outranks a plausible success, and read the failures first.

Capabilities are fixed earlier than you think

An entire overnight run produced nothing because an isolation feature had decided at session start that the directory was not a repository — we created the repository two hours later, and the feature never re-checked. Establishing a precondition mid-flight does not unlock a capability that was resolved at launch. Prove any load-bearing capability on one cheap case before committing a fleet and a night to it.

A regenerator drops what it is not told to carry

Three times, a script that rebuilt a document or index silently discarded fields it had not been explicitly told to preserve — including, once, the record of two known defects. Anything regenerated needs a carry-forward list, and the carry-forward needs its own check.
