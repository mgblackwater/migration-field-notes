The approach

Finding out what a system actually does

Before you can rebuild a system you have to know what it is — and the ways teams usually find out are quietly broken. This is the method that worked for us, with the receipts from where the usual methods failed.

01The trap of counting what you can see

Our first plan was a list of screens — dozens of them. It felt rigorous: a crawler had walked the running application in every role, taken hundreds of screenshots, and the plan was derived from them. Derived — that was its virtue over a hand-written list.

But that number was never a count of what the system does. It was a count of what a camera could reach. A screenshot crawler cannot photograph a stored procedure, a scheduled job, an endpoint no screen calls, or a rule that lives in a permission matrix. When we later derived the feature list properly, roughly half the features had no screen at all — including the calculation the entire system existed to produce, which lived in stored procedures and was visible to nothing the crawler could see.

The general form

Every discovery method has a blind spot shaped exactly like the thing it cannot observe — and its output never warns you. The screenshot plan didn't say “I am blind to batch jobs”. It just had no rows for them, and an absent row looks identical to an absent feature.

02Six sources, read independently

The fix is not a better single method. It is several methods whose blind spots do not overlap — read independently, so that agreement means something.

SourceWhat it can tell youWhat it cannot
The front-end source Every page, its address, the endpoints it calls — including pop-up dialogs no crawler opens Whether any of it still works on the server
Screenshots of the running system What a real user is shown, role by role — the only source for “who sees which rows” Anything with no screen to photograph
The written specification Intent, and rules nobody would guess from code Anything built after it was written — and ours contradicted itself again and again
The permission workbooks Thousands of individual access decisions, cell by cell Everything that is not a permission
The live database Structure, cascades, what is actually populated Any rule at all — ours had zero constraints, so nothing was enforced in storage
The stored procedures The arithmetic — in our case the only place the core calculation existed Anything about the user interface

Why independence matters: two readers agreeing after reading different evidence is corroboration. Two readers agreeing after reading the same document is an echo. We ran each reading blind to the others and only then reconciled: hundreds of findings, dozens of contradictions, dozens of open questions — and no single source came close to seeing every feature. The contradictions were not noise to be smoothed away; each one was a question with an owner.

Rule that came out of this

Derive every number from an artifact that changes when reality changes. A hand-written inventory has no oracle, so it stays wrong quietly. What one label called “the batch jobs” turned out to be four different true counts wearing one costume — the repositories, the shipped programs, the scheduled registrations, and the jobs that actually recur, no two equal — and no document could have caught it, because every document was copying another document. A fifty-line script reading the scheduler's own configuration caught it immediately, and keeps catching it.

03A feature is not a screen

The single most useful reframing of the whole engagement: tag every feature with where it actually lives, because that decides the shape of the work and — more important — what can judge it.

SurfaceThe unit of workThe oracle that judges it
A page people useA screen slice — the page plus the endpoints behind itA screenshot of the old screen, plus response comparison
Endpoints with no pageA contract slice The old system's response bodies
A scheduled jobA job slice The rows it writes, diffed against an old run
Logic inside the databaseNot a rewrite. A characterization harness over the existing procedures The procedure itself — a golden master
Nothing found anywhereAn investigation, never an inventionNone yet — that is the point

Filing everything as “screens” prices a golden-master harness over financial arithmetic as if it were a form with a grid — and that mispricing is invisible until someone builds the wrong thing well.

04Verify the plan by building against it

A plan is a theory about the work. Ours met reality in one long automated run: batches of workers attempting every unbuilt piece, each instructed that an honest failure with a precise reason beats a faked success.

OutcomeShareMeaning
Built, compiling, checks passingJust under two-thirds Real progress, with a caveat the lessons page owns
Partly built — stopped at a real obstacleA few Each named, with what is missing
Blocked on a human answerA few more Each named, with the question it waits on
Aimed at things that do not existAbout a fifth The most valuable output of the run

Only a single batch reported the plan had described its work accurately. A whole block of rows named routes the legacy could not even serve — a whole navigation section existed in the source tree but was commented out of the application, and our route scanner read the routing files without stripping comments. A handful of features our sources had written off as “no trace anywhere” all existed when a batch was sent to investigate rather than invent — one of them fully configured in production. And two of our scariest documented risks turned out to be false: the “destructive” void operation changed a status flag and deleted nothing, and the “unrecoverable” archival cascade was soft-delete all the way down.

What to copy

Treat the first build pass across a legacy-replacement plan as an instrument for falsifying the plan, not as delivery. Require every worker to report plan-accurate / partly-wrong / wrong with evidence, and read those verdicts before celebrating the completion count. Ours cost one night and corrected months of planning assumptions.
