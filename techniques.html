The techniques

Everything here has a name

We reinvented half of these before learning they had names, literatures, and known lists of ways they go wrong. Knowing the names buys you the pitfalls other people already paid for. Each card: what it is, where it bites, and where to read more.

Characterization testing

Michael Feathers · also called pinning tests
What
Tests that capture what a system currently does — not what it should do. Write an assertion you know is wrong, run it, paste the actual behaviour in as the expected value. The test then guards that behaviour, bugs included, while you change the code underneath.
Why it matters
It is the formal name for “parity, not correction”. On our engagement, an obvious-looking fix to a financial calculation would have doubled a downstream figure — proven by experiment. Characterize first; argue about correctness afterwards, with the business, on the record.
Watch out
A characterization test is only as strong as the inputs it captures. Two identical records characterize almost nothing. Companion ideas worth knowing: seams (places behaviour can be altered without editing code) and sprout method (grow new code beside old instead of editing it).
Read
Working Effectively with Legacy Code, Feathers · understandlegacycode.com · Uncovering the Seams in Mainframes

Golden master & approval testing

Emily Bache, Llewellyn Falco · also snapshot testing
What
Capture an entire output — a report, a response, a rendered screen — as an approved artifact, and fail on any diff. The first run records the master; every later run compares. Cheap, broad coverage over code you don't yet understand.
Why it matters
The right tool for report-heavy legacy systems: approve the old report's output once, then diff the rebuild against it forever. Our screenshot pairs and recorded golden outputs were exactly this.
Watch out
Masters recorded from a bad fixture bless the bad fixture. Noise — dates, row order, float formatting — must be scrubbed or every run is a false alarm, and teams learn to ignore the harness. And never source the expected values from the system under test: that is the circular oracle from the lessons.
Read
Bache — Approval Testing · ApprovalTests.Net · the Gilded Rose kata — do it once; it teaches more than reading

Parallel run / shadow testing

Sam Newman · GitHub's Scientist · also dark launching
What
Run old and new implementations side by side on the same inputs, compare results, and keep exactly one as the source of truth. GitHub's Scientist library wraps the old path as “control” and the new as “candidate”, publishes mismatches, and never lets candidate errors reach users.
Why it matters
The strongest verification available when old and new share a database: replay the same requests against both, diff the responses. Mismatches are data to triage, not failures — some will be the old system's noise.
Watch out
Side effects. A parallel run of anything that writes — submissions, emails, outbound files — doubles the writes unless the candidate is sandboxed. Most of the literature on this pattern is really about that one problem.
Read
github/scientist · Scientist.NET · Zalando — Parallel Run · Monolith to Microservices ch. 3

Response diffing at the proxy

Twitter's Diffy · the two-primaries trick
What
A proxy multicasts every request to three instances: the new code, and two identical copies of the old code. Differences between the two old copies measure the system's natural noise; only new-code differences that exceed that noise get reported.
Why it matters
The two-primaries idea is the insight worth stealing even without the tool: it separates “changed behaviour” from “non-deterministic anyway” — the two things every naive diff harness conflates.
Read
opendiffy/diffy (maintained fork) · the original · a worked migration example with NGINX

Strangler fig

Martin Fowler · with event interception and divert-the-flow
What
Grow the new system around the old, intercepting traffic at the edges and routing one capability at a time to the replacement until the old system is hollow. The point is operational: rollback is a routing change, never a deploy.
Why it matters
With a shared database underneath, per-path routing at a gateway lets old and new serve different capabilities over the same data during the transition — which is also what makes parallel runs cheap to wire in.
Read
Strangler Fig Application · Divert the Flow

Patterns of Legacy Displacement — and the feature-parity trap

Cartwright, Horn & Lewis (Thoughtworks) · the umbrella series
What
The most complete modern treatment of replacing old systems: how to break the problem up, which transitional structures to build knowing you will demolish them, and a catalogue of named patterns — Transitional Architecture, Legacy Mimic (the new system impersonating the old to its unchanged neighbours), Event Interception, and more.
The warning label
Feature Parity — replicating an old system faithfully on a new stack — is called a trap by the authors outright: “people greatly underestimate the effort required.” Our engagement measured it: when we finally built against our parity plan, only a single batch found the plan accurate, and a whole block of planned pieces targeted things the old system could not even serve. Read it as the argument for shrinking scope to the flows that carry value — not as a prohibition on parity where regulation or funding arithmetic genuinely demands it.
Read
the series · Feature Parity · Transitional Architecture · Legacy Mimic

Branch by abstraction & expand-contract

Paul Hammant · Danilo Sato · the in-codebase versions
What
For replacing a component inside a codebase you keep shipping: put an abstraction over the old implementation, grow the new one behind it, flip, remove. Expand-contract is the same shape for interfaces and schemas — add the new alongside the old, migrate callers, then remove. Never a breaking change in one step.
Read
Fowler — Branch by Abstraction · Hammant's original · Parallel Change

Anti-corruption layer

Eric Evans, Domain-Driven Design
What
A translation layer between the new system and a legacy model you do not want leaking in. The new code speaks its own clean language; the layer does the dirty conversion at the border.
Why it matters
Two borders demanded it on our engagement: an outbound file hand-off to an external costing system, and a frozen legacy schema whose misspelled columns and unlabelled integer codes should stop at the data layer rather than spread through a new front end.
Read
Microsoft's pattern page — the concise version; Evans' book for the full argument
Also worth knowing

The Mikado Method (Ellnestam & Brodwall) — plan a large change by attempting it, reverting, and graphing what blocked you; the formal version of what a failed build pass teaches by accident. And dark launching — a parallel run whose new path is invisible to users; the reason a batch-mode harness comes first when there is no production traffic to shadow yet.
